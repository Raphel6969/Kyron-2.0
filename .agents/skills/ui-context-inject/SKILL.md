# WHEN TO LOAD
Load once per project after `design-system` completes and before the first `ui-build` call. Also invoke when a screen feels tonally wrong or domain-generic.

# INPUTS
- `docs/01-problem.md` (Domain, personas, market context)
- `design/DIRECTION.md` (Declared reference sites, 5 color tokens)
- The product's primary data entity (inferred from solution doc — e.g. "attrition risk score", "transaction anomaly", "credit application")

# OUTPUTS
- `design/CONTEXT.md` — 10-bullet product personality card

# EXECUTION PROTOCOL

Read the three input files above. Then write `design/CONTEXT.md` answering each of the following 10 bullets with specifics derived from the product — no generic filler allowed.

```markdown
# Product Personality — design/CONTEXT.md
_Generated by ui-context-inject. Read this before writing any layout or component code._

1. **Who uses this tool and in what environment?**
   e.g. "Indian IT ops lead at a desk, reviewing flagged employees before a quarterly review meeting — not browsing, not exploring."

2. **What does the primary screen need to feel like?**
   e.g. "A command center. One dominant risk table consuming 70% of the viewport. Supporting metrics to the right. Nothing decorative."

3. **What is the emotional register of the product?**
   e.g. "Serious, precise, calm. This is a decision-support tool — not a consumer app. No celebration animations, no friendly mascots."

4. **What two reference sites are closest in domain tone?**
   e.g. "Linear (information density, precise borders) and Axiom.co (real-time data density, dark ops aesthetic)."

5. **What is the single typography decision that matters most?**
   e.g. "The risk score number must be the largest element on any card — larger than any label or description."

6. **What motion should NOT do on this product?**
   e.g. "No bouncy easings, no celebration confetti, no slide-in-from-everywhere chaos. Motion should only confirm data arrival or state change."

7. **What does the hero need to communicate in 3 seconds?**
   e.g. "That the system already knows which employees are at risk — show a live-looking risk table as the hero, not a marketing tagline."

8. **What is the primary data entity and how should it look?**
   e.g. "An employee risk card: dark raised surface, left severity bar (red/amber/green), name + role + top SHAP factor, risk score right-aligned."

9. **What should a first-time user see on an empty state?**
   e.g. "A single CTA: 'Upload your HR export or connect your HRIS'. No empty table. No abstract illustration."

10. **What would make a judge stop and say 'this looks real'?**
    e.g. "A table with 30+ seeded employees, real Indian names, real tenure/overtime data, SHAP attribution text that reads like a real HR note."
```

Write the actual answers — not the example prompts. Use information from `docs/01-problem.md` and the product domain. Every bullet must be product-specific.

# EXIT CRITERIA
- [ ] `design/CONTEXT.md` exists with all 10 bullets answered with product-specific content
- [ ] No bullet contains placeholder text or generic SaaS filler
- [ ] `ui-build` can read this file and derive concrete layout constraints from it
